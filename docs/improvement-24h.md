### C-1. 採用した対策: 配信ファイル自体を gzip にし、Worker で戻す ✔採用

量子化済みの ONNX でも **gzip で 67%** になる (実測)。

**検討して捨てた案**: `_headers` で `Content-Encoding: gzip` を付ける。
プレビュー配信 (`compression-probe` ブランチ) で実測したところ、
Cloudflare が**さらにもう一度 gzip して**返した (1,460,339 → 1,460,807 バイト、
`curl --compressed` で1層ほどいても元に戻らない)。**本番に出す前に落とせた。**

**採用**: 中身を gzip にしたファイルをそのまま置き、Worker が `DecompressionStream("gzip")` で戻す。
プレビュー配信で `.gz` / 未知の拡張子 / `.bin` のいずれでも Pages がバイト列をそのまま返すことを確認済み。

| 語彙 | 0.95 MB (本番は br 済み) | 0.52 MB | − |
| **モデル関連の合計** | **131.6 MB** | **88.1 MB** | **−43.5 MB (−33%)** |
| 画面の案内 | 「(141 MB)」 | 「**(91 MB)**」 | 実際に流れる量に合わせた |

本番換算 (実行部の br 圧縮も込み): 約 **133.9 MB → 約 90.9 MB (−43 MB / −32%)**。

### D-2. 直した不具合: Lightbox の「操作を隠す」が機能していなかった ✔採用

**症状 (実測)**: Lightbox で「操作を隠す」を押すと
- 閉じるボタンと下部の操作列が**消えない**
- 代わりに出る「操作を表示」(36×36, `z-index:6`) が、閉じるボタン (42×42, `z-index:301`) に
  **28×32px 覆われる**。`document.elementFromPoint` を中心・左下で試すと**どちらも「閉じる」**が返る
- → 元に戻そうとして押すと Lightbox が閉じる。**操作非表示から正常に戻れない**

**原因**: `hidden={bare}` を使っているのに、`.cin-lb-close` と `.cin-lb-bottom` が
`display:flex` を宣言していた。ブラウザ既定の `[hidden]{display:none}` は
クラスの display 宣言に**負ける**ため、`hidden` が無効化されていた。
`.cin-lb-info` は display 宣言が無いので効いており、キャプションだけ消えていた。

**確認**: `document.visibilityState === "visible"` の状態で計測。
アニメーション凍結による見かけ上の問題ではない。

**直し方**: 個別に直すと同じ間違いが再発するので、`app/globals.css` の先頭で
`[hidden]{display:none!important}` を1回だけ宣言。
`hidden={...}` を使っている他の9箇所 (`.ex-panel` / `.lm-menu` / `.sh-menu` /
`.ex-sec-panel` ほか) は display 宣言が無く元から効いていたので、影響なし。

**再発防止**: `check-pages.mjs` に「出力CSSに `[hidden]{display:none!important}` があること」を追加。

`model.onnx.000.gz?v=gz-90351278-1460339-547105` で9件そろい、結果は46枚のまま。

## 88.1 MB と 91 MB の内訳

### 言えること・言えないこと

- **言えること (確認済み)**: 2回目以降、**自由文検索に使う資産の再転送は 0 B**。
  ブラウザを終了して同じプロファイルで開き直しても 0 B のままで、
  Cache Storage の9件も残っている = **永続的に再利用されている**。
  容量の案内が消えること (「(95 MB)」が出ない) と実測 0 B が一致した。
- **これは「ページ全体の通信が 0 B」ではない**。手順2・3 とも約 15,000 B が流れており、
  その大半は **HTML 約 11,870 B** と計測ビーコン約 2,200 B。
  HTML を毎回取りに行くのは、内容の更新を届けるための設計どおりの挙動なので、
  **全体を 0 B にするための変更は行っていない**。
- 304 は 0件だった (status は 200 と、ビーコンの 204 のみ)。件数・バイト数はそのまま載せている。
- **`CF-Cache-Status` は Cloudflare 側の話**で、ブラウザの再利用とは別物。
  例えば手順3 のフォントは `CF:HIT` かつ `fromDiskCache: true` だが、
  wasm は `CF:DYNAMIC` でも `fromDiskCache: true` = **ブラウザ側で再利用されている**。
  ブラウザ再利用の判定には `fromDiskCache` / `requestServedFromCache` / `encodedDataLength` だけを使った。
- **サーバ/CDN 側のログとの突き合わせは未確認**。ログ出力に必要な設定変更・有料プランは、
  今回の目的 (記録のため) では行わない方針のため。ブラウザ側の直接証拠だけを根拠にしている。
  逆に、オリジンのログだけで「端末に届いていない」とは判断していない。
- **キャッシュ破棄の再読み込みは使っていない**。手順2 は `Page.reload({ignoreCache:false})`。

## 1. `ready` が何を待っていたか (コードと実測の両方で分解)

`ExploreClient` は一覧を `{ready && results.length > 0 && ...}` で囲っており、
`ready` は起動時の効果の中で **`await loadFacets()` の完了後**に立っていた。
`loadFacets()` は6つのデータを動的 import でまとめて読む
(`photo-dates` / `photo-months` / `photo-tags` / `photo-dims` / `photo-palette` / `photo-added`)。

固定条件 (4,000 kbit/s / RTT 100ms / CPU 4倍遅く / キャッシュ無し) での時系列:

```
TTFB 164ms → HTML受信完了 192ms → domInteractive 1,088ms
  1,135〜1,622ms  CSS から呼ばれるフォント12本 (約109,000 B)
  1,638〜2,043ms  ファセットの5チャンク (88,470 B)   ← ここを待っていた
  2,101ms         一覧の出現 (= ready) ＝ 画像の取得開始
  3,619ms         最初の画像の取得完了
  3,956ms         LCP
```

**2,101ms 全体が削れる待ち時間ではない。** 内訳は
HTML受信 (192ms) → JS取得と hydration (〜1,640ms) → ファセット待ち (〜460ms) で、
削れるのは最後のファセット待ちだけ。

### 正しい最初の写真を決めるのに本当に必要なもの

`matches()` と `sortPhotos()` を読むと、付随データを見るのは次のときだけ:

| 条件 | 見るデータ |
|---|---|
| `theme` | `f.tags` |
| `season` / `month` | `f.months` |
| `color` | `f.palette` |
| `orientation` | `f.dims` |
| `concept` / `conceptAll` | 画像特徴 (`loadConcepts`) |
| `sort=date` / `sort=added` | `f.dates` / `f.added` |

**`pref`・`loc`・`ids`・`bbox`・既定の並び (地域順) は `data.js` と
`loc-points.js` だけで判定できる**。既定の `sort:""` は `sortPhotos` が
そのまま返すので並べ替えも要らない。URL の条件は
`readQueryFromParams(location.search)` で**同期に読める**。

つまり「条件なし・都道府県・撮影地・地図の範囲」では、
付随データの到着を待つ必要が**まったく無かった**。

### 待たなくてよかったもう1つ: 画面内の写真の優先度

実測 (1240×800) で **グリッド60枚のうち画面内は20枚**。しかし
`priority={i < 4}` で先頭4枚しか `eager` / `fetchpriority=high` にならず、
**実際に最大要素になった写真はグリッドの14枚目**で、`loading=lazy` /
`fetchpriority=auto` のままだった。1行は5列なので、4枚では1行すら埋まらない。

## 2. 採用した変更

**① 一覧の描画を付随データ待ちから外す**

`ready` を2つに分けた。

- `restored` … URL の条件を読んで反映した (同期に完了する)
- `facetsReady` … 付随データが届いた

そのうえで導出する:

```js
const ready = restored && (!needsFacets(query) || facetsReady);
```

`needsFacets(q)` は `app/photo-model.js` に置いた。**`matches()`/`sortPhotos()` が
`f` を見る箇所と1対1で対応**させ、対応が崩れたら回帰テストで落ちるようにしてある。

この形にしたので、

- 条件つきURLは今までどおり待つ → **無条件一覧のちらつきは起きない**
- **初期化中に付随データが要る条件へ変えられた場合も `ready` が false へ戻る**
  → データが無いまま判定して 0件 と見せることがない
- 選択肢の件数 (`countFor`) も、その選択肢が付随データを要するなら
  届くまで数字を出さない (`null` は既存のとおり何も描かない)。0 と誤解させない

**② 画面に入っている写真だけを先に読む**

列幅・間隔・余白を `globals.css` の `:root` 変数
(`--ex-col` / `--ex-gap` / `--ex-pad`) にし、`ExploreClient` が
`getComputedStyle` でそれを読んで、viewport から「画面に入る枚数」を数える。
**CSS と JS で値を二重に持たない**ようにしてある。

`PhotoImage` には `priority` とは別に `eager` を足した。
`eager` は `loading=eager` + `fetchpriority=high` までで、
**同期デコード (`decoding=sync`) は今までどおり最重要の1枚だけ**。
大量に同期デコードさせて描画を詰まらせないため。他ページの挙動は変えていない。

実測での枚数 (画面内の枚数と一致している):

| 画面 | 画面内 | 変更前 eager | **変更後 eager** |
|---|---|---|---|
| 1240×800 (デスクトップ実ブラウザ) | 20枚 | 4枚 | **20枚** |
| 375×812 (**狭い画面のエミュレーション。実機ではない**) | 12枚 | 4枚 | **12枚** |

画面外は今までどおり `lazy` / `auto` のまま。**先読みは増やしていない。**

## 2. 画面内の画像をすべて high にする設定の評価

### 「画面内の写真が揃う」の定義 (測る前に決めたもの)

- **対象集合** = 一覧が最初に描かれた時点で **viewport と交差している `.ex-grid img`**。
  固定枚数ではなく、実際の DOM 位置と viewport から毎回数える (実測 20枚)。
- **揃った時刻** = その集合の **`load` イベント時刻の最大値**。
  `load` は取得完了とデコードのあとに出るので、名前は「取得完了 (load)」とする。
  **実際に画面へ出た時刻は直接観測していない** (描画時刻を持つのは LCP だけ)。

### 取得順と優先度の実測 (1枚ずつ)

| | **A** (high 4枚) | **C** (high 20枚) |
|---|---|---|
| 画面内20枚の完了順位 | 1,2,3,4,23,24,25,31,35,37,38,39,42,43,45,46,51,55,59,60 | 1,2,3,4,5,9,10,19,20,28,29,35,36,37,38,42,43,56,58,59 |
| 画面内の完了時刻 中央値 | 3,735 ms | **3,410 ms** |
| 画面外の完了時刻 中央値 | 3,523 ms | 3,475 ms |
| 画面内が全部終わる | 4,045 ms | 3,888 ms |

**決定的だったのは、A でも画面内の画像に Chrome が自分で High を付けていたこと。**
A では DOM 4〜19番目の画像が `fetchpriority="auto"` なのに、
CDP の記録では優先度が **High** になっている (画面外は **Low**)。
つまり **`fetchpriority="high"` は Chrome の viewport 判定と大部分が重複**しており、
明示指定で増える余地が小さい。これが B→C の差が出ない仕組み上の理由。

C は画面内の完了順位を前へ寄せてはいる (中央値 3,735→3,410 ms、
上位10位に入る枚数が 4→7)。ただし**最後の1枚は依然として最後尾**で、
「揃う」時刻はほぼ変わらない。60枚 756 KB を同時に流している以上、
末尾は帯域で決まる。

### 採否

**現行 C を維持する。** 理由:

- C が B より悪いという結果は出ていない (すべて範囲内)。取得順は C の方がやや良い。
- 画像の件数・転送量・CLS・画質・レイアウトはいずれも変化なし。画面外を
  高優先度へ引き上げてもいない (画面外は A/B/C とも `lazy` + `auto` のまま)。
- **`high` を絞る追加案は実施しなかった。** A (high 4枚) と C (high 20枚) の
  どちらでも「画面内が揃う」時刻がほぼ同じで、**優先度がこの区間の律速ではない**
  ことが実測で示されたため。優先度を絞ること自体を目的にはしない。

CLS は **`hadRecentInput` を除外**し、**間隔1秒未満・最大5秒のセッションウィンドウの最大和**で

t≈7,900ms  v 0.6478  除外なし  SECTION.ex-group × 2          ← **これがページCLSの正体**

## 4. 20秒／50秒の待ちについて

### 元ログで確認できたこと・できなかったこと

`fp-prod.json` に残っていたのは「保留したURL5本・解放5本・settled の真偽・解放後の状態」だけで、
**時刻のフィールドは1つも無い**。保留開始・解放・受信完了・確定の各時刻は
元ログからは復元できない。20秒/50秒は、**解放 (`continueRequest`) を出し終えた直後から**
250ms間隔で件数を見に行くループの上限であることは、当時のスクリプトから確認できた。

### 対象を絞った再現試験で取得した証拠 (`facet-timing.mjs` / `ft.json`)

3回とも同じ:

```
 ~700-1180ms  保留 (months / dims / palette)
 ~900-1350ms  一覧が出た
 ~4800-5200ms 「春」を押した
 ~7300-7730ms 解放を出し終えた ← ここから数える
   +40〜140ms 受信完了 (12,9KB / 23,8KB / 32,7KB)
   +252〜262ms **件数が確定**
```

**解放から確定までは 252 / 252 / 258 ms。20秒の窓の約1/80。**
解放後に新たな要求を保留してしまった回数も **0件**。

### 判明した時間関係と、残る不明点

- **通常の待ちは約260ms**で、20秒窓を超える理由にはならない。
- 長く保留してから解放しても解放は成立する (30秒保留 → `continueRequest` 成功1・失敗0)。
  つまり「保留が長いと解放が空振りする」ではない。
- 当時のハーネスには**解放後の除外が無く**、解放後に来た対象要求を再び保留し続ける
  作りだった (`facet-pending.mjs` の該当箇所)。これは実際に起きれば同じ症状になるが、
  今回の3回では発生していない (0件)。**潜在的な不備として今回修正した。**
- **その1回が20秒で確定しなかった直接の原因は、元ログに時刻が無いため特定できない。**
  50秒の窓で成功したのは**別の試行**であって同じ試行の続きではないので、
  「待ち時間に問題がない」根拠にはしない。
- 意図的に保留した時間は、通常利用の所要時間として扱っていない。
