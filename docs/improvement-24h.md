### C-1. 採用した対策: 配信ファイル自体を gzip にし、Worker で戻す ✔採用

量子化済みの ONNX でも **gzip で 67%** になる (実測)。

**検討して捨てた案**: `_headers` で `Content-Encoding: gzip` を付ける。
プレビュー配信 (`compression-probe` ブランチ) で実測したところ、
Cloudflare が**さらにもう一度 gzip して**返した (1,460,339 → 1,460,807 バイト、
`curl --compressed` で1層ほどいても元に戻らない)。**本番に出す前に落とせた。**

**採用**: 中身を gzip にしたファイルをそのまま置き、Worker が `DecompressionStream("gzip")` で戻す。
プレビュー配信で `.gz` / 未知の拡張子 / `.bin` のいずれでも Pages がバイト列をそのまま返すことを確認済み。

| Dense | 1.50 MB | 1.39 MB | −0.11 MB |
| 語彙 | 0.95 MB (本番は br 済み) | 0.52 MB | − |
| **モデル関連の合計** | **131.6 MB** | **88.1 MB** | **−43.5 MB (−33%)** |
| 画面の案内 | 「(141 MB)」 | 「**(91 MB)**」 | 実際に流れる量に合わせた |

本番換算 (実行部の br 圧縮も込み): 約 **133.9 MB → 約 90.9 MB (−43 MB / −32%)**。

### D-2. 直した不具合: Lightbox の「操作を隠す」が機能していなかった ✔採用

**症状 (実測)**: Lightbox で「操作を隠す」を押すと
- 閉じるボタンと下部の操作列が**消えない**
- 代わりに出る「操作を表示」(36×36, `z-index:6`) が、閉じるボタン (42×42, `z-index:301`) に
  **28×32px 覆われる**。`document.elementFromPoint` を中心・左下で試すと**どちらも「閉じる」**が返る
- → 元に戻そうとして押すと Lightbox が閉じる。**操作非表示から正常に戻れない**

**原因**: `hidden={bare}` を使っているのに、`.cin-lb-close` と `.cin-lb-bottom` が
`display:flex` を宣言していた。ブラウザ既定の `[hidden]{display:none}` は
クラスの display 宣言に**負ける**ため、`hidden` が無効化されていた。
`.cin-lb-info` は display 宣言が無いので効いており、キャプションだけ消えていた。

**確認**: `document.visibilityState === "visible"` の状態で計測。
アニメーション凍結による見かけ上の問題ではない。

**直し方**: 個別に直すと同じ間違いが再発するので、`app/globals.css` の先頭で
`[hidden]{display:none!important}` を1回だけ宣言。
`hidden={...}` を使っている他の9箇所 (`.ex-panel` / `.lm-menu` / `.sh-menu` /
`.ex-sec-panel` ほか) は display 宣言が無く元から効いていたので、影響なし。

**再発防止**: `check-pages.mjs` に「出力CSSに `[hidden]{display:none!important}` があること」を追加。

### C-3. Worker のURLにも版を付ける ✔採用 (公開直後に本番で実測した問題)

fetch('/ort/text-worker.js')                      →  9,839バイト (旧版)

**確認**: 新しいビルドで Cache Storage の項目が
`model.onnx.000.gz?v=gz-90351278-1460339-547105` で9件そろい、結果は46枚のまま。

| その他の検索用データ | ORT wasm 9.55 MiB (このハーネスは無圧縮) | 同一 9.55 MiB |
| **検索に必要な合計実転送量** | **141.65 MiB** / 12リクエスト | **98.18 MiB** / 12リクエスト |
| サーバ側の実効レート | 249,915 B/s | 248,805 B/s |
| 取得 (0→100%) | **551.8 s** | **372.1 s** |
| 準備 (取得完了→結果) ※wasm取得+ORT初期化を含む | 554.6→594.9 = **40.3 s** | 374.0→414.3 = **40.3 s** |
| **実行操作から最初の結果まで** | **594.9 s (9分55秒)** | **414.3 s (6分54秒)** |
| 推論のみ (モデル常駐、押してから結果まで) | **148 ms** | **89 ms** |
| 結果 | 46枚 | **46枚 (一致)** |

**区間の定義**: 「取得」= 実行ボタンを押してから進捗が100%になるまで。
「準備」= 進捗100%から結果表示まで (ORT wasm の取得と ONNX セッション作成を含む、直列)。
「実行操作から最初の結果まで」は独立に測った値であり、区間の足し算ではない。

**削減率の対比 (足し算で推定していないこと)**

| | 削減 |
|---|---|
| モデルの転送量 | 131.56 → 88.08 MiB = **−33.0%** |
| 検索に必要な合計転送量 | 141.65 → 98.18 MiB = **−30.7%** |
| **待ち時間 (押してから結果まで)** | 594.9 → 414.3 s = **−30.4%** |

取得区間だけなら −32.6% だが、**準備の 40.3 秒は縮まない**ため、
体感の待ち時間の削減は転送量の削減率より小さい。「33%減ったから33%速い」ではない。

なお、この 40.3 秒の大半は ORT wasm 9.55 MiB の取得 (250,000 B/s で 39.2 秒)。
**本番では wasm は Cloudflare が brotli で約 2.68 MiB にして返す**ので、
この区間は本番のほうが短い。ハーネスは wasm を圧縮しないため、両版とも同じだけ長く出ている。

**写真の取得はこの帯域制限の対象外** (外部 `landscapes-images.pages.dev` 配信)。
モデル配信だけに掛けた制限であって、サイト全体の回線再現ではない。

## 88.1 MB と 91 MB の内訳

どちらも **1,048,576 で割った値 (MiB)** を「MB」と表記している。算出対象が違う。

| | バイト数 | MiB | 何を含むか |
|---|---|---|---|
| `TEXT_DOWNLOAD_BYTES` (報告の 88.1MB) | 92,358,722 | **88.08** | ONNX 86.17 + Dense 1.39 + 語彙 0.52。**閲覧側の Worker が自分で数えられる分**。進捗の分母 |
| `TEXT_MODEL_TOTAL_BYTES` (画面の案内) | 95,000,257 | **90.60** | 上記 + 実行部 wasm 2.52 |
| 画面表示 | `Math.round(90.60)` | **91** | 案内文の「(91 MB)」 |

差の 2.52 MiB は **ORT の wasm ちょうど**。wasm は ORT 自身が取りに行くので進捗に数えられないが、
利用者から見れば必要な通信なので、案内には足している。**表示は仕様どおりで誤りではない。**

十進 MB なら 90.60 MiB = 95.0 MB。表記は MiB を「MB」と書く一般的な流儀に合わせている。

**ただし1点、見積りが甘い箇所を見つけた**: `wasmOnWire` が2種類の wasm の gzip 後サイズの
`Math.min` を取っていた。実際に多くのブラウザが取得するのは SIMD 版 (2.68 MiB) で、
選ばれていたのは非SIMD版 (2.52 MiB)。**少なめに見積もる向き**なので `Math.max` に直した。
直しても 88.08 + 2.68 = 90.76 → 表示は **91 MB のまま**変わらない。

## 圧縮が可逆であることの照合

配信している `.gz` を展開して、元のモデルと **sha256 で一致**することを確認した。

```
7分割を展開して連結  135,377,779 B  sha256 fbc8fbeaa5237d96bd1bf430057c70d3…
元の ONNX            135,377,779 B  sha256 fbc8fbeaa5237d96bd1bf430057c70d3…  → 完全一致
```

前版 (`4b5349b`) が配っていた無圧縮ファイルとも直接比較し、
ONNX・Dense・語彙の**3つとも byte 単位で一致**。閲覧側が受け取る中身は同じで、
検索品質が変わる余地がない。実測でも両版とも「窓に映る街並み」46枚・「雨の夜のネオン看板」50枚。

## 残る3項目

前回「内蔵ブラウザペインでは確かめられない」と記録した2件を、
**インストール済みの Microsoft Edge を DevTools Protocol で直接動かして**確認した。
新しい依存は追加していない (Node 標準の WebSocket と `fetch` のみ)。
利用者のプロファイルは触らず、使い捨ての `--user-data-dir` を使っている。

### A4. Enter / Space ✔ 確認できた

Edge 152 / 本物のキーイベント (`Input.dispatchKeyEvent`、`windowsVirtualKeyCode` つき)。

**対照実験**: ページ内に素の `<button>` を作って Enter を送ると
`keydown {key:"Enter", code:"Enter", keyCode:13, isTrusted:true}` が届き、**click が1回**発火した。
内蔵ペイン (keyCode:0 で click 0回) との違いは環境差であることが確定した。

| 操作 | 結果 |
|---|---|
| 入力欄から Tab 1回 → 「この言葉で探す (91 MB)」 | ✔ 到達。フォーカス枠 `solid 2px rgba(220,190,100,.9)` |
| そこで **Enter** | ✔ **実行された** (「読み込み中 0% 中止」へ) |
| 入力欄から Tab 1回 → 「中止」 | ✔ 到達。同じフォーカス枠 |
| そこで **Space** | ✔ **中止された** (「中止しました / もう一度試す (91 MB)」) |
| 入力欄から Tab 1回 → 「もう一度試す (91 MB)」 | ✔ 到達 |
| そこで **Enter** | ✔ **再開された** (「読み込み中 0%」) |

**IME 変換確定の Enter との区別**: 入力欄には `onkeydown`/`onkeypress` が無く、
Enter で検索が走る経路そのものが存在しない (実行はボタンのみ)。
したがって変換確定の Enter で誤実行することはない。

### A3. /ort/*.wasm の HTTPキャッシュ ✔ 確認できた

同じ使い捨てプロファイルで Edge を2回起動し、**サーバ側の送出バイト数**で確認した
(ヘッダやモデルのキャッシュ状況を根拠にしていない)。

| | サーバが送出した量 | 内訳 |
|---|---|---|
| 1回目 (プロファイル新規) | **100.70 MiB / 95 リクエスト** | モデル9ファイル 88.08 MiB + **`/ort/ort-wasm-simd.wasm` 9.55 MiB** + HTML/JS/CSS/フォント |
| 2回目 (同じプロファイルで開き直し) | **0.00 MiB / 1 リクエスト** | その1件は集計API (`/__tally`) 自身。**wasm を含め、何も取りに行っていない** |

どちらも結果は **46枚で一致**。
→ モデルは Cache Storage から、**wasm・Worker・ort.min.js・HTML・JS・CSS・フォントは
ブラウザのHTTPディスクキャッシュから**再利用されている。
「モデルだけ再利用された」ではなく、**検索に必要な全データが再取得ゼロ**であることを実測で確認した。

**更新時に古いWorkerと新しいモデルが混ざらないこと**: 取得URLに版を付けてある
(`model.onnx.000.gz?v=gz-…`、`text-worker.js?v=bc1bb867bd70`)。
版はファイルの中身から作るので、中身が変われば必ず別URLになり、
30日キャッシュを持っていても古い実体を掴まない。
公開直後に実際に起きた新旧混在 (上の C-3) は、この版付けで解消済み。

### A2. 実機スマホ ✗ 未確認のまま

- Chrome 拡張は未接続 (`list_connected_browsers` が空)。
- computer-use MCP はブラウザを **read 階層**でしか許可しないため、クリック・入力ができない。
- 物理端末は接続されていない。

今回 Edge を直接動かせるようになったが、**これはデスクトップの実ブラウザであって実機スマホではない**。
画面幅・UA・タッチ点数を変えたエミュレーションを実機確認とは呼ばない。
→ 実機で確認するには、Chrome 拡張を接続するか、端末を USB で繋いで
`--remote-debugging` 経由で同じ手順 (写真閲覧・自由文検索・読み込み中のLightbox開閉・中止・再試行) を通す必要がある。
